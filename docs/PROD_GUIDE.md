# Прод, деплой и CI в Graham Analyzer — объяснение с нуля

Это не справочник команд (он в [DEPLOY.md](DEPLOY.md)), а объяснение: что
как устроено, зачем, и что делать в каждой жизненной ситуации — от первой
выкатки до исправления ошибки в пятницу вечером.

---

## 1. Две машины: разработка и прод

Сейчас всё живёт на вашем компьютере:

```
Ваш компьютер (разработка)
├── Postgres в Docker (graham_postgres, порт 5432)
├── uvicorn --reload на :8000        ← бэкенд, перезапускается при каждом сохранении
├── npm start на :3000               ← фронт, тоже пересобирается на лету
├── ~/Reports/<тикер>/*.pdf          ← отчёты
├── LLM-ключи, Playwright            ← разбор PDF, сбор раскрытий
└── .env                             ← локальные настройки
```

Это **среда разработки**: удобно править, всё перезапускается само, ошибки
видны сразу. Для посетителей она не годится: `npm start` — это отладочный
сервер, uvicorn с `--reload` следит за файлами, порты торчат наружу, пароль
базы `12345678`.

**Прод** (production, «боевой» стенд) — отдельный сервер в интернете, где
сайт работает для всех:

```
Сервер (прод)                         снаружи открыты только 80 и 443
┌──────────────────────────────────────────────────────────────────┐
│  web (Caddy)  ← :443 https://ваш-домен                           │
│    ├── /            → готовая сборка фронта (статические файлы)  │
│    └── /api/...     → backend:8000                               │
│                                                                  │
│  backend (uvicorn, 1 процесс)                                    │
│    ├── API                                                       │
│    └── планировщик: цены в 19:00, ставки, прогрев кэша           │
│                                                                  │
│  db (Postgres 18)  ← данные на томе pg_data                      │
└──────────────────────────────────────────────────────────────────┘
```

Ключевое решение нашего проекта: **сервер только показывает данные.** Разбор
PDF, LLM, Playwright, проверка отчётов — всё остаётся на вашей машине. На
сервер приезжает готовая база. Поэтому серверу не нужны ни отчёты, ни
LLM-ключи, ни браузеры — он маленький и простой.

```
Ваш компьютер                           Сервер
  разобрали отчёт, проверили  ──push-data.sh──►  база обновлена
  написали код, проверили     ──git push──► GitHub ──git pull──► пересобрали
```

## 2. Docker на пальцах: образ, контейнер, том

Docker вы уже используете для Postgres. Разберём три понятия на нашем бэкенде.

**Образ (image)** — это «замороженная» коробка со всем, что нужно программе:
Linux-основа, Python 3.13, все пакеты из `requirements.txt` и **код
бэкенда**. Образ собирается по рецепту — `Dockerfile` — и после сборки не
меняется.

**Контейнер** — запущенный экземпляр образа. Из одного образа можно запустить
сколько угодно контейнеров. Контейнер можно остановить, удалить и создать
заново — он одноразовый.

**Том (volume)** — папка, которая живёт отдельно от контейнера. Всё, что
должно пережить пересоздание контейнера, лежит на томе:

| Том | Что там | Если удалить |
|---|---|---|
| `pg_data` | вся база | данные потеряны (поэтому бэкапы) |
| `caddy_data` | сертификаты HTTPS | Caddy получит новые, ничего страшного |

Отсюда главное правило, которое отвечает на ваш вопрос про пересборку:

> **Код живёт в образе, данные — на томе.**
> Поменяли код → пересобираете образ и пересоздаёте контейнер.
> Поменяли данные → ничего не пересобираете, данные на томе.

Почему код запекается в образ, а не подкладывается с диска, как в
разработке? Потому что тогда то, что работает на сервере, — это ровно то,
что собрано и проверено: те же версии пакетов, тот же код. Не бывает «у
меня работало, а на сервере нет, потому что там другой Python».

**docker compose** — описание нескольких контейнеров одним файлом
(`deploy/docker-compose.prod.yml`): какие сервисы, из каких образов, какие
тома и порты, кто от кого зависит. Одна команда поднимает всё.

## 3. Файлы прод-конфига — по одному

### `backend/Dockerfile` — рецепт образа бэкенда

```dockerfile
FROM python:3.13-slim                 # основа: Debian + Python 3.13
WORKDIR /app
COPY backend/requirements.txt ...     # сначала ТОЛЬКО список пакетов
RUN pip install -r ...                # ставим пакеты
COPY backend/ backend/                # потом весь код
COPY tools/edisclosure-scraper/ ...   # бэкенд импортирует скрапер
RUN useradd ... app; USER app          # работаем не от root
CMD alembic upgrade head && uvicorn ... --workers 1 --proxy-headers
```

Почему сначала `requirements.txt`, а код потом? Из-за **кэша слоёв**. Каждая
строка Dockerfile — слой. При пересборке Docker идёт сверху вниз и берёт
слои из кэша, пока ничего не изменилось. Изменили код, но не список пакетов —
`pip install` (минута-две) берётся из кэша, пересобирается только слой с
кодом (секунды). Если бы код копировался до `pip install`, любая правка
запятой переустанавливала бы все пакеты.

Что происходит при старте контейнера (`CMD`):

1. `alembic upgrade head` — применяет новые миграции к базе. На пустой базе
   создаёт всю схему, на актуальной ничего не делает. Поэтому миграции на
   сервере руками запускать не нужно.
2. `uvicorn ... --workers 1` — один процесс. Почему не четыре: планировщик
   живёт внутри приложения, и при четырёх воркерах ежедневное обновление цен
   шло бы четыре раза. Для нашей нагрузки одного хватает с запасом (ответы из
   кэша — 10–30 мс).
3. `--proxy-headers` — бэкенд стоит за Caddy и видит адрес Caddy, а не
   посетителя. Caddy передаёт настоящий адрес в заголовке `X-Forwarded-For`,
   и этот флаг велит uvicorn ему верить. Нужно для ограничения попыток входа:
   иначе все посетители выглядели бы как один адрес.

### `deploy/web.Dockerfile` — сайт: двухэтапная сборка

```dockerfile
FROM node:24-alpine AS build           # этап 1: сборщик
RUN npm ci                             # пакеты (1500 штук, долго)
ENV REACT_APP_API_URL=/api             # ← важно, см. ниже
RUN npm run build                      # → папка build/ со статикой

FROM caddy:2-alpine                    # этап 2: то, что поедет на сервер
COPY --from=build /src/build /srv      # только готовые файлы
```

Фронт в проде — это **не программа, а файлы**: `index.html`, один большой
`main.xxxx.js`, CSS, шрифты. Их собирает `npm run build`, и после этого Node
не нужен вообще. Поэтому этап 1 (Node + 300 МБ `node_modules`) выбрасывается,
а в итоговый образ попадает Caddy и папка со статикой — десятки мегабайт.

**Важная ловушка:** `REACT_APP_API_URL` подставляется в код **во время
сборки**, а не при запуске. После `npm run build` строка `/api` уже вшита в
`main.js`. Значит, сменить адрес API без пересборки фронта нельзя. Для нас
это не проблема — адрес всегда `/api`, — но помнить стоит.

Почему `/api`, а не отдельный домен вроде `api.сайт.ru`? Страница и API на
одном домене → браузер считает их одним сайтом → cookie входа (`SameSite=Strict`)
работает, CORS не нужен, сертификат один.

Локально `REACT_APP_API_URL` не задан, и фронт ходит на
`http://localhost:8000`, как раньше (`frontend/src/services/companies.api.ts`).

### `deploy/Caddyfile` — веб-сервер

Caddy делает четыре вещи:

1. **HTTPS сам.** Увидел домен в `SITE_ADDRESS` → сходил в Let's Encrypt,
   получил сертификат, продлевает его раз в два месяца. Без certbot и cron.
   Условие: домен уже смотрит на сервер (A-запись в DNS) и порты 80/443
   открыты.
2. **`/api/*` → бэкенд.** `handle_path` срезает `/api`: браузер просит
   `/api/screen/market`, бэкенд получает `/screen/market` — в коде бэкенда
   ничего менять не пришлось.
3. **Всё остальное — статика.** `try_files {path} /index.html`: если файла
   нет (`/company/171` — это не файл, а адрес внутри React-приложения),
   отдаётся `index.html`, и React сам рисует нужную страницу.
4. **Кэширование статики.** Файлы в `/static/` имеют хэш в имени
   (`main.3ab8abf9.js`) — их браузер хранит год: при новой сборке имя
   изменится. `index.html` и адреса страниц — `no-cache`: браузер каждый раз
   спрашивает, не вышла ли новая версия. Так после выкатки посетители сразу
   получают свежий фронт, а не старый из кэша.

### `deploy/docker-compose.prod.yml` — всё вместе

Три сервиса. На что обратить внимание:

- У `db` и `backend` **нет `ports`** — они видны только внутри сети Docker.
  Снаружи доступен только `web` (80, 443). Базу из интернета не достать
  даже при утёкшем пароле.
- `depends_on: condition: service_healthy` — бэкенд стартует, только когда
  Postgres ответил на `pg_isready`. Иначе миграции упали бы на ещё не
  готовой базе.
- `restart: unless-stopped` — упал или сервер перезагрузился → Docker сам
  поднимет. Не поднимет, только если вы остановили руками.
- `healthcheck` у бэкенда раз в 30 секунд дёргает `/health` — в
  `docker compose ps` видно `healthy` / `unhealthy`.

### `deploy/.env.prod` — секреты и настройки

Создаётся на сервере из `deploy/env.prod.example`, **в git не попадает**
(есть в `.gitignore`). Репозиторий публичный: всё, что в git, видят все.
Поэтому пароль базы, `SECRET_KEY`, пароль почты, токен T-Invest — только
здесь, с правами `600` (читает только владелец).

Изменили `.env.prod` → пересобирать не надо, достаточно пересоздать
контейнер: `up -d` (см. раздел 6).

### `.dockerignore`

Что **не** отправлять Docker при сборке: `.env`, `backups/`, `venv/`,
`node_modules/`, логи, cookies скрапера. Две причины: скорость (не гонять
гигабайты) и безопасность (секреты не должны оказаться внутри образа).

## 4. Сервер: подготовка один раз

### Что арендовать

- **В России** — у нас есть учётные записи посетителей, это персональные
  данные, 152-ФЗ требует хранить их в РФ. Timeweb Cloud, Selectel, Yandex
  Cloud, REG.RU — любой.
- **2 ядра, 2–4 ГБ памяти, 20–40 ГБ диска.** Ubuntu 24.04 LTS.
- Памяти 2 ГБ впритык для сборки фронта (React-сборка ест 1–1,5 ГБ). Если
  взяли 2 ГБ — обязательно сделайте swap (ниже).
- Домен: купить у регистратора, в DNS добавить **A-запись** `@` (и `www`,
  если нужен) → IP сервера. Распространяется от минут до нескольких часов —
  сделайте заранее.

### Первый вход и защита

```bash
# у себя: ключ, если ещё нет
ssh-keygen -t ed25519
ssh-copy-id root@IP_СЕРВЕРА

# на сервере
adduser deploy                       # рабочий пользователь
usermod -aG sudo deploy
mkdir -p /home/deploy/.ssh && cp ~/.ssh/authorized_keys /home/deploy/.ssh/
chown -R deploy:deploy /home/deploy/.ssh

# вход только по ключу, root по ssh — нет
sudo sed -i 's/^#\?PasswordAuthentication .*/PasswordAuthentication no/; s/^#\?PermitRootLogin .*/PermitRootLogin no/' /etc/ssh/sshd_config
sudo systemctl restart ssh           # ДО этого проверьте в другом окне: ssh deploy@IP работает

# файрвол: только ssh и веб
sudo ufw allow OpenSSH && sudo ufw allow 80 && sudo ufw allow 443 && sudo ufw enable

# автоматические обновления безопасности
sudo apt install -y unattended-upgrades

# swap 2 ГБ (если памяти 2 ГБ)
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### Docker

```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker deploy       # чтобы docker без sudo; перелогиньтесь
docker compose version               # проверка
```

**Внимание про ufw и Docker:** порты, опубликованные Docker (`ports:`),
обходят ufw. У нас опубликованы только 80/443 у Caddy, и их мы и так
открываем — поэтому это не дыра. Но никогда не добавляйте `ports:` базе или
бэкенду в прод-компоуз.

### Сокращение для команд

Все команды compose на сервере длинные. Один раз:

```bash
echo "alias dc='docker compose -f /opt/graham/deploy/docker-compose.prod.yml --env-file /opt/graham/deploy/.env.prod'" >> ~/.bashrc
source ~/.bashrc
```

Дальше в гайде `dc` — это оно.

## 5. Первая выкатка

```bash
# 1. Код
sudo mkdir -p /opt/graham && sudo chown deploy /opt/graham
git clone https://github.com/gosgosling/graham-analyzer.git /opt/graham
# репозиторий публичный — для чтения ключи GitHub не нужны

# 2. Настройки
cd /opt/graham/deploy
cp env.prod.example .env.prod && chmod 600 .env.prod
nano .env.prod
#   SITE_ADDRESS=ваш-домен.ru
#   ALLOWED_ORIGINS=https://ваш-домен.ru   PUBLIC_SITE_URL=https://ваш-домен.ru
#   POSTGRES_PASSWORD=$(openssl rand -base64 32)   — сгенерируйте и вставьте
#   SECRET_KEY=...                                  — так же
#   почта, токен T-Invest

# 3. Сборка и запуск
dc up -d --build                      # первый раз долго: npm ci + сборка фронта
dc ps                                 # все три — running, backend — healthy
dc logs -f backend                    # видно миграции и «Планировщик запущен»
```

После шага 3 у вас работающий сайт **с пустой базой** (схема есть, данных
нет). Открываете `https://домен` — должен быть зелёный замок.

```bash
# 4. Данные — с ВАШЕЙ машины
SERVER=deploy@ваш-домен.ru ./deploy/push-data.sh

# 5. Администратор — на сервере
dc exec backend python -m scripts.create_admin

# 6. Бэкап по расписанию — на сервере
crontab -e
#   15 4 * * *  /opt/graham/deploy/backup.sh >> /home/deploy/backup.log 2>&1
```

Готово. Дальше сервер живёт сам: в 19:00 обновляет цены, раз в минуту
проверяет, не пора ли прогреть кэш, в 4:15 делает бэкап.

## 6. Как вносить изменения — главный раздел

### Короткий ответ на «всегда пересобирать контейнер?»

**Код — да, данные — нет.** И пересборка — это не страшно и не долго
благодаря кэшу слоёв:

| Что изменили | Что пересобирается | Сколько | Простой сайта |
|---|---|---|---|
| Python-код бэкенда | слой `COPY backend/` | секунды | ~10 с, пока бэкенд перезапускается |
| `requirements.txt` | `pip install` + код | 1–3 мин | ~10 с |
| Код фронта | `npm run build` | 1–2 мин | ~1 с |
| `package.json` / lock | `npm ci` + сборка | 5–15 мин | ~1 с |
| `Caddyfile` | только слой с ним | секунды | ~1 с |
| `.env.prod` | ничего | — | ~10 с |
| Данные (отчёты) | ничего | — | 0 (бэкенд перезапускается ~10 с) |

Простой короткий, потому что **сборка идёт, пока старый контейнер работает**.
Docker сначала собирает новый образ, и только потом за секунды меняет старый
контейнер на новый. Посетитель в худшем случае увидит несколько секунд
ошибки 502 от Caddy («бэкенд не отвечает») — и то только при перезапуске
бэкенда.

`dc up -d --build` пересоздаёт **только те контейнеры, чей образ или
настройки изменились**. Поменяли фронт — бэкенд и база не трогаются.

### Сценарий А: новая фича или исправление в коде

Это основной цикл, и он всегда одинаковый:

```
1. Локально: правите, смотрите в браузере (npm start + uvicorn --reload — как сейчас)
2. Локально: тесты          cd backend && venv/bin/python -m pytest -q
                            cd frontend && npx tsc --noEmit && CI=true npx react-scripts test --watchAll=false
3. git commit, git push
4. GitHub: CI прогоняет то же самое на чистой машине → зелёная галочка у коммита
5. Сервер:                  cd /opt/graham && git pull && dc up -d --build
6. Проверка: открыли сайт, dc logs --tail 50 backend
```

Шаг 4 — страховка от «у меня работало»: CI ставит всё с нуля по
`requirements.txt` и `package-lock.json`. Именно так нашёлся `APScheduler`,
которого не было в `requirements.txt`: локально он стоял в venv, а на чистой
машине бэкенд бы не запустился.

**Правило: на сервер — только зелёные коммиты.** Красный CI — сначала
чините.

### Сценарий Б: новые отчёты / правка данных

Код не менялся — пересобирать нечего.

```
1. Локально: разобрали PDF, проверили в админке (как сейчас)
2. Локально: SERVER=deploy@домен ./deploy/push-data.sh
```

Что делает `push-data.sh`:

1. Выгружает вашу локальную базу **без таблиц входа** (`users`,
   `user_sessions`, `auth_tokens`) — учётные записи посетителей живут только на
   сервере, и если бы мы заливали их тоже, каждая выкатка стирала бы всех
   зарегистрированных.
2. Копирует файл на сервер.
3. На сервере: делает бэкап (на случай, если залили что-то не то),
   заменяет таблицы данных, перезапускает бэкенд.

Кэш расчётов сам увидит новые данные, через минуту фоновый прогрев всё
пересчитает.

### Сценарий В: изменение схемы базы (миграция)

Например, добавили колонку в `financial_reports`. Порядок важен:

```
1. Локально: модель + миграция alembic, alembic upgrade head на своей базе, тесты
2. git push → CI зелёный
3. Сервер: git pull && dc up -d --build
   → бэкенд при старте сам применит миграцию (alembic upgrade head в CMD)
4. Только теперь: push-data.sh
```

Почему сначала код, потом данные: `push-data.sh` заливает таблицы в формате
**вашей** схемы. Если на сервере схема старая, восстановление упадёт (или,
хуже, бэкенд не поймёт новые данные). Выкатили код → схемы совпали → можно
данные.

Миграции должны быть **совместимы со старыми данными**: добавить колонку с
`NULL` — можно; удалить колонку, которую ещё читает код, — сначала выкатить
код, который её не читает, потом миграцию.

### Сценарий Г: поменять настройку

```bash
nano /opt/graham/deploy/.env.prod
dc up -d          # без --build: compose видит, что окружение изменилось, и пересоздаёт контейнер
```

### Сценарий Д: что-то сломалось после выкатки (откат)

Код откатывается через git — сервер просто собирает предыдущую версию:

```bash
cd /opt/graham
git log --oneline -5                 # найти последний рабочий коммит
git checkout abc1234                 # переключиться на него
dc up -d --build                     # собрать и запустить его
# починили у себя, запушили — вернуться на свежий код:
git checkout main && git pull && dc up -d --build
```

Удобно ставить метку перед каждой выкаткой — тогда откат по имени:

```bash
git tag deploy-2026-10-17 && git push --tags     # у себя, перед выкаткой
git checkout deploy-2026-10-17                    # на сервере, при откате
```

Данные откатываются из бэкапа (раздел 7). Миграции назад (`alembic downgrade`)
для нашего масштаба не стоят риска — проще восстановить бэкап, сделанный
перед выкаткой.

### Сценарий Е: срочно починить в пятницу вечером

Тот же сценарий А, без исключений. Соблазн «поправлю прямо на сервере в
файле» — главный источник бардака: правка не в git, при следующем `git pull`
либо конфликт, либо она молча потеряется, и ошибка вернётся. На сервере код
не правится никогда — только `git pull`.

## 7. Повседневная жизнь сервера

### Посмотреть, что происходит

```bash
dc ps                          # кто запущен, healthy ли
dc logs -f backend             # журнал бэкенда в реальном времени (Ctrl+C — выйти)
dc logs --tail 100 web         # последние 100 строк Caddy: запросы, ошибки сертификата
dc exec db psql -U graham graham_analyzer      # консоль базы
docker stats                   # память и процессор по контейнерам
df -h                          # место на диске
```

### Что делает сервер сам

| Когда | Что | Где |
|---|---|---|
| 19:00 МСК | цены Мосбиржи и T-Invest, ключевая ставка, ОФЗ, индексы, выпуски акций, нефть | `app/scheduler.py` |
| раз в минуту | если данные изменились — прогрев кэша (скринер, сравнение, оценки) | `services/cache_warmup.py` |
| каждый час | удаление истёкших сессий входа | `scheduler.py` |
| 4:15 | бэкап базы | cron → `deploy/backup.sh` |
| раз в 2 месяца | продление сертификата | Caddy сам |

### Бэкапы

`backup.sh` кладёт дамп в `~/graham-backups`, хранит 14 последних.
**Бэкап на том же сервере — не бэкап**: сервер умер — бэкапы вместе с ним.
Минимум — раз в неделю забирать себе:

```bash
# у себя
scp deploy@домен:~/graham-backups/$(ssh deploy@домен 'ls -t ~/graham-backups | head -1') ~/projects/git_clone/graham-analyzer/backups/
```

Лучше — `BACKUP_REMOTE` в cron (rsync в облачное хранилище или на вашу машину).

Восстановление:

```bash
dc exec -T db pg_restore -U graham -d graham_analyzer --clean --if-exists --no-owner < файл.dump
dc restart backend
```

Бэкап, который ни разу не восстанавливали, — не бэкап. Один раз проверьте
восстановление у себя (через тестовый стенд, раздел 10).

### Обновления

- Ubuntu сама ставит обновления безопасности (`unattended-upgrades`).
- Базовые образы (Python, Postgres, Caddy, Node) раз в месяц:
  `dc build --pull && dc up -d` — скачает свежие версии с исправлениями.
- Postgres: в компоузе зафиксирована **основная версия 18**. Переход на 19 —
  это отдельная процедура через дамп, само по себе не случится.

## 8. CI — что это и что делает у нас

**CI (continuous integration)** — робот, который на каждый `git push`
берёт чистую машину, ставит проект с нуля и прогоняет проверки. Результат —
зелёная галочка или красный крестик у коммита на GitHub.

Зачем, если тесты можно запустить у себя? Три причины:

1. **Чистая машина.** У вас локально venv, `node_modules`, кэши, `.env` —
   всё накопленное за месяцы. CI ничего этого не имеет и ставит ровно по
   `requirements.txt` / `package-lock.json` — как сервер. Пропущенная
   зависимость ловится здесь, а не на проде.
2. **Не забудешь.** Проверки идут всегда, даже когда лень.
3. **История.** У каждого коммита видно, был ли он рабочим — удобно искать,
   какой коммит что сломал, и выбирать, на что откатываться.

### Наш файл: `.github/workflows/ci.yml`

Запускается при `push` в `main`, на pull request и вручную (кнопка
«Run workflow»). Три задачи:

**backend** — Python 3.13, `pip install -r requirements.txt`, `pytest`.
Базе тесты не нужны: расчёты проверяются на заглушках. Около 2 минут.

**frontend** — Node 24, `npm ci`, затем:
- `tsc --noEmit` — проверка типов TypeScript;
- `eslint --max-warnings 18` — линтер. Сейчас в старом коде 18
  предупреждений (неиспользуемые переменные в админке и т.п.). CI их
  терпит, но **19-е — уже ошибка**. Это «храповик»: новых не добавляем,
  починили старое — уменьшите число в `ci.yml`;
- jest-тесты;
- `npm run build` — сборка, как для прода.

**images** — запускается, только если первые две зелёные. Собирает оба
боевых образа (`backend/Dockerfile`, `deploy/web.Dockerfile`) и проверяет,
что бэкенд в образе импортируется. Ловит ошибки в Dockerfile и
`.dockerignore` до сервера.

### Где смотреть

GitHub → репозиторий → вкладка **Actions**. Или кружок у коммита на
главной: жёлтый — идёт, зелёный — всё хорошо, красный — что-то упало.
Для публичного репозитория Actions бесплатны без ограничений по минутам.

### CI красный — что делать

1. Actions → упавший запуск → упавшая задача → упавший шаг → лог.
2. Найти первую ошибку (не последнюю — последняя обычно следствие).
3. Повторить ту же команду у себя — команды в `ci.yml` те же, что вы
   запускаете руками.
4. Починить, запушить — CI перезапустится сам.

Если упало «у меня работает, в CI нет» — почти всегда разница окружения:
пакет стоит у вас, но не в `requirements.txt`; файл есть у вас, но в
`.gitignore`; тест зависит от вашего `.env`.

### CI ≠ CD

**CD (continuous delivery/deployment)** — когда робот после зелёного CI сам
выкатывает на сервер. У нас его **нет, и это сознательно**: до конференции
выкатка — руками, одной командой, когда вы решили. Меньше движущихся частей,
нет SSH-ключа от сервера в настройках GitHub, и всегда понятно, что на
сервере.

Когда захочется автоматизировать (после конференции), два пути:

- **Простой:** в CI добавить шаг «по SSH зайти на сервер и выполнить
  `git pull && dc up -d --build`». Ключ — в секретах GitHub.
- **Правильный:** CI собирает образы и кладёт в реестр (GitHub Container
  Registry), сервер их только скачивает (`dc pull && dc up -d`). Плюс: сервер
  ничего не собирает — не нужен swap под сборку фронта, выкатка за секунды,
  а откат — просто запуск предыдущего образа. Минус: больше настройки.

## 9. Ветки и порядок работы

Вы работаете один, поэтому без сложных схем:

- **`main` = то, что можно выкатывать.** Каждый коммит в `main` должен
  проходить CI.
- Мелкое (поправить текст, исправить баг) — прямо в `main`.
- Крупное и долгое (новый раздел, переделка расчёта) — в ветке
  `feature/имя`, пушите её сколько угодно (CI проверит и её через pull
  request), в `main` — когда готово.
- Перед выкаткой — метка `deploy-ГГГГ-ММ-ДД` (раздел 6, сценарий Д).
- После заморозки 12.10 — в `main` только исправления.

## 10. Проверить прод у себя, без сервера

Тот же стенд можно поднять на своей машине — так он и проверялся:

```bash
cd deploy
cp env.prod.example .env.prod
# в .env.prod:
#   SITE_ADDRESS=:80                                   (без домена и HTTPS)
#   ALLOWED_ORIGINS=http://localhost:8080
#   PUBLIC_SITE_URL=http://localhost:8080
#   COOKIE_SECURE=false
#   HTTP_PORT=8080
#   HTTPS_PORT=8443
#   POSTGRES_PASSWORD, SECRET_KEY — любые
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
# сайт: http://localhost:8080 — с пустой базой

# залить данные из локальной базы (то же, что push-data.sh, без ssh):
EX=(); for t in users user_sessions auth_tokens; do EX+=(-T $t -T ${t}_id_seq); done
docker exec graham_postgres pg_dump -U graham_user -Fc --no-owner --no-acl "${EX[@]}" graham_analyzer > /tmp/data.dump
set -a; . ./.env.prod; set +a
docker compose -f docker-compose.prod.yml --env-file .env.prod exec -T db \
  pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner --single-transaction < /tmp/data.dump

# убрать всё (и тестовую базу):
docker compose -f docker-compose.prod.yml --env-file .env.prod down -v
rm .env.prod
```

Он не мешает разработке: другие порты (8080), свой проект в Docker
(`graham`), своя база на своём томе.

## 11. Когда что-то не так

| Симптом | Где смотреть | Частая причина |
|---|---|---|
| Сайт не открывается вообще | `dc ps`, `dc logs web` | контейнер `web` упал; порты 80/443 закрыты в ufw или у провайдера |
| Нет HTTPS, ошибка сертификата | `dc logs web` | DNS ещё не смотрит на сервер; `SITE_ADDRESS` с опечаткой |
| Страница есть, данных нет, 502 | `dc logs backend` | бэкенд упал или перезапускается; ошибка в миграции |
| Бэкенд `unhealthy`, перезапускается по кругу | `dc logs backend` | ошибка импорта (пакета нет в requirements), база недоступна |
| Вход не работает, CSRF в логах | `.env.prod` | `ALLOWED_ORIGINS` не совпадает с адресом сайта (https, без `/` в конце) |
| Вход не держится | `.env.prod` | `COOKIE_SECURE=true` при открытии по http |
| Цены не обновились | `dc logs backend \| grep Планировщик` | токен T-Invest; Мосбиржа не ответила — догонит на следующий день |
| Сборка фронта убита (`Killed`) | `dmesg \| tail` | не хватило памяти — нужен swap |
| Кончилось место | `df -h`, `docker system df` | старые образы: `docker image prune -a` |
| После выкатки видна старая версия фронта | — | жёсткое обновление страницы (Ctrl+Shift+R); если у всех — не пересобрали `web` |

## 12. Словарь

- **Прод (production)** — боевой стенд для посетителей. **Dev** — ваша
  машина для разработки.
- **Деплой, выкатка** — доставить новую версию на прод и запустить.
- **Образ / контейнер / том** — рецепт-коробка / запущенная коробка /
  папка, которая переживает коробку (раздел 2).
- **Reverse proxy** — сервер, который принимает запросы снаружи и раздаёт
  их внутренним сервисам. У нас Caddy.
- **Статика** — файлы, которые отдаются как есть, без программы: собранный
  фронт.
- **Миграция** — скрипт изменения схемы базы (alembic).
- **CI** — автоматические проверки на каждый push. **CD** — автоматическая
  выкатка после них (у нас нет).
- **Откат (rollback)** — вернуть предыдущую рабочую версию.
- **Healthcheck** — регулярная проверка «жив ли сервис».
